# منصة الرقابة الصحية — نسخة المزامنة

تتكون المنصة من واجهة ثابتة على GitHub Pages، وواجهة برمجية على Render، وقاعدة PostgreSQL دائمة. تظهر جميع الزيارات لجميع الحسابات؛ يستطيع صاحب الزيارة والأدمن حذفها. إدارة الحسابات والإضافات والنسخ الاحتياطي متاحة للأدمن فقط، وتُفرض الصلاحيات في الخادم.

## النشر

1. أنشئ مستودع GitHub وارفع **محتويات هذا المجلد** إلى جذره، بما فيها الملف المخفي `.github/workflows/pages.yml` والملف `render.yaml`. لا ترفع كلمات مرور أو نسخ بيانات إلى المستودع.
2. في Render، أنشئ Blueprint من المستودع. ينشئ `render.yaml` خدمة ويب وقاعدة PostgreSQL؛ راجع خطة القاعدة وتكلفتها ومدة الاحتفاظ قبل التأكيد. ستحتاج إلى القاعدة الدائمة، وليس ملفات القرص المؤقتة في خدمة الويب.
3. أدخل متغيرات البيئة المطلوبة في إعدادات Render:
   - `ALLOWED_ORIGIN`: أصل موقع GitHub Pages فقط، مثل `https://USERNAME.github.io` دون مسار المستودع أو شرطة أخيرة. للدومين الخاص استخدم أصله بالضبط.
   - `ADMIN_NAME`: الاسم الثلاثي الأولي للأدمن.
   - `ADMIN_PASSWORD`: كلمة مرور قوية للأدمن من 16 حرفاً على الأقل. هذه كلمة مرور الأدمن؛ المستخدمون العاديون يدخلون برمز من أربعة أرقام.
   - ينشئ Blueprint متغير `APP_PEPPER` ويربط `DATABASE_URL` بقاعدة البيانات. احتفظ بقيمة `APP_PEPPER` بأمان ولا تغيرها بعد إنشاء الحسابات: تغييرها يجعل كلمات المرور المخزنة غير قابلة للتحقق.
4. عند اكتمال نشر خدمة Render انسخ رابطها HTTPS، وعدّل `config.js` بوضعه بدل `https://YOUR-RENDER-SERVICE.onrender.com` دون `/` في النهاية، ثم ارفع التعديل إلى GitHub. لا تضع كلمة مرور أو سراً في هذا الملف.
5. من إعدادات المستودع **Settings → Pages → Build and deployment** اختر **GitHub Actions**. انشر الفرع `main` أو شغّل إجراء Publish GitHub Pages يدوياً. افتح عنوان Pages بعد نجاح الإجراء وسجّل دخول الأدمن بالاسم وكلمة المرور المحددين في Render.
6. من زر **الإدارة** أضف المستخدمين بأسمائهم الثلاثية ورمز من أربعة أرقام، وسلم لكل مستخدم رمزه بطريقة آمنة. تستطيع إيقاف حساب أو إعادة تعيين رمزه؛ كلا الإجراءين ينهي جلساته السابقة.

يُنشأ حساب الأدمن الأول فقط عند بدء الخادم وقاعدة المستخدمين لا تحتوي أدمن. تغيير `ADMIN_PASSWORD` أو `ADMIN_NAME` بعد ذلك لا يغير الحساب الموجود؛ لا تحذف قاعدة البيانات لإعادة الضبط. جهّز إجراء استعادة آمن وقاعدة احتياطية قبل الاستخدام الفعلي. تشارك الأجهزة البيانات بعد تسجيل الدخول؛ تُحدّث الزيارات عند فتح السجل وعند العودة للصفحة ودورياً كل 30 ثانية أثناء ظهورها. يلزم الاتصال بالإنترنت للحفظ.

## نقل بيانات النسخة القديمة

على الجهاز والمتصفح اللذين يحتويان الزيارات القديمة، افتح النسخة القديمة، وصدّر النسخة الاحتياطية JSON منها. بعد نشر النسخة الجديدة، سجّل دخول الأدمن واختر **الإدارة ← استيراد نسخة JSON**. يتم الدمج ولا تُحذف النسخة الأصلية. يؤدي استيراد الملف نفسه مرة أخرى إلى تكرار البيانات، وتُنسب السجلات المستوردة للأدمن المستورد. التخزين المحلي للنسخة القديمة لا ينتقل تلقائياً إلى نطاق GitHub Pages المختلف.

## ملاحظات الأمان والتشغيل

- يحفظ الخادم تجزئات مشفّرة للرموز مع ملح و`APP_PEPPER`، ولا يحفظ الرموز كنص صريح. تُقفل الحسابات مؤقتاً بعد خمس محاولات خاطئة متتالية، وتُحدّ الطلبات أيضاً على مستوى الخادم. الرموز ذات أربعة أرقام محدودة القوة؛ استخدم HTTPS، واحمِ متغيرات Render، ولا تستخدم هذا النمط وحده لبيانات عالية الحساسية.
- تخزن جلسة المتصفح رمز وصول في `sessionStorage` وتستمر لمدة أقصاها سبعة أيام؛ تسجيل الخروج وإيقاف الحساب وتغيير الرمز يبطل الجلسة من الخادم. لا تستخدم حساب الأدمن على جهاز مشترك دون تسجيل الخروج.
- لا تُحذف قاعدة البيانات عند إعادة نشر خدمة الويب، لكن توفر البيانات يعتمد على خطة قاعدة Render ونسخها الاحتياطية. راجع سياسة انتهاء القاعدة والنسخ والاستعادة في حسابك، وأنشئ نسخاً احتياطية دورية من لوحة الإدارة.
- لم تُنشر هذه الحزمة تلقائياً. إعداد المستودع، ورابط Render، ومتغيرات البيئة، ونشر GitHub Pages مطلوبة لتشغيلها عبر الأجهزة.

## اختبار محلي للمطور

ثبّت `backend/requirements-dev.txt` للاختبار (أو `backend/requirements.txt` للتشغيل فقط)، ثم شغّل الخادم مع `DATABASE_URL` و`APP_PEPPER` و`ALLOWED_ORIGIN` و`ADMIN_NAME` و`ADMIN_PASSWORD` مضبوطة. شغّل `python3 -m unittest discover -s tests` من جذر المشروع لاختبارات API باستخدام SQLite مؤقتة. لاختبار PostgreSQL، مرّر عنوان قاعدة اختبار فارغة في `HEALTH_TEST_DB`. الاختبارات تنشئ بيانات داخل قاعدة الاختبار؛ لا تستخدم قاعدة إنتاج.
